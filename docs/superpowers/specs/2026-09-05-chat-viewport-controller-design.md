# Chat Viewport Controller — Design

**Date:** 2026-09-05
**Status:** Approved, ready for implementation planning

## Problem

The chat viewport moves when the reader did not ask it to. On desktop this was
traced to messages remounting, fixed in `8d4e475` by making persisted Codex
message ids survive a reread. On mobile it persists: backgrounding iOS Safari
while an agent is generating and then returning can still shift the view, and
so can ordinary generation.

The cause is structural rather than a single defect. Six independent writers
can move the viewport, three of them on timers, and two disagreeing values
answer the question "is the reader at the bottom".

## Current writers

| writer | site | timing |
| --- | --- | --- |
| initial bottom-pin | `useChatSessionState.ts:473` | rAF loop, up to 60 frames |
| prepend / load-all restore | `useChatSessionState.ts:435` | layout effect |
| follow on new message | `useChatSessionState.ts:808` | `setTimeout 50ms` |
| external-update follow | `useChatSessionState.ts:617` | `setTimeout 200ms` |
| send | `useChatComposerState.ts:899` | `setTimeout 100ms` |
| search jump / bookmark jump | `useChatSessionState.ts:711`, `BookmarkRail.tsx:104` | `scrollIntoView` / `scrollTo` |

Timers fire after paint, so each correction is a visible jump rather than an
invisible adjustment. Overlapping timers are the flakiness.

The two sources of truth are the `isUserScrolledUp` state, updated from scroll
events, and the live `isNearBottom()` computation (`useChatSessionState.ts:327`,
a 50px threshold). The follow path reads the first; the external-update path
reads the second.

### Why mobile is worse

- iOS Safari's dynamic toolbar changes the container's `clientHeight` by
  roughly 60–100px. `isNearBottom()` measures distance from the bottom, so the
  toolbar alone can flip the answer without the reader moving.
- Backgrounding drops the websocket. Returning reconnects, which dispatches
  `websocket_reconnected` (`WebSocketContext.tsx:139`), bumps
  `externalMessageUpdate`, and runs `refreshFromServer` followed by a delayed
  `scrollToBottom` — a full list replacement and a post-paint scroll landing
  together, while iOS is restoring its own scroll position.
- Safari's native scroll anchoring is weaker than Chrome's, and the desktop fix
  relies on it.

## Behaviour contract

**Returning to the app never moves the reader.** If they were reading
mid-transcript they stay there; if they were parked at the bottom they stay
there and following resumes.

This is the whole contract. "Returning from background" is then not a case the
code knows about — it falls out of holding position generally.

## Design

A new hook, `useChatViewport`, becomes the only writer of `scrollTop`.

### State

A mode, `following` or `anchored`. When anchored it also holds an anchor
element and `viewportOffset`, that element's offset from the top of the
viewport.

### The single effect

One `useLayoutEffect` with no dependency array, so it runs after every commit,
before paint:

- `following` → `scrollTop = scrollHeight`
- `anchored` → `scrollTop = anchorEl.offsetTop - viewportOffset`

Holding one element visually still makes prepend-restore, load-all restore,
reflow compensation, remount recovery and return-from-background the same
operation instead of five. The assignment is idempotent, so overlapping commits
cannot fight each other, and running pre-paint makes corrections invisible.

Anchoring is only viable because message ids are now stable across a store
refresh (`8d4e475`). Before that the anchor element was destroyed on every
refresh, which is what broke the browser's own anchoring.

### Transitions

| trigger | mode |
| --- | --- |
| user scrolls to the bottom | `following` |
| user scrolls away from the bottom | `anchored`, re-anchor |
| send a message, or press "scroll to bottom" | `following` |
| search hit or bookmark jump | `anchored` on the target element |

Nothing else changes the mode.

### Re-anchoring cost

On a scroll event, recompute `viewportOffset` for the element already held —
one layout read. Pick a new element only when the current one has left the DOM
or drifted more than one viewport away. A `querySelectorAll` per scroll event
would be O(messages) on a 1300-message transcript.

### The iOS toolbar rule

Track the container's `clientHeight` between scroll events. When it has
changed, treat the event as layout-induced: re-anchor, but do not re-evaluate
the mode. This is what stops a toolbar hide/show from flipping the reader into
`following` and pinning them to the bottom.

Anchored mode needs no such guard — it compares element offsets, not distance
from the bottom, so `clientHeight` does not enter the arithmetic.

### Writes must not be read back as user intent

The scroll listener ignores events generated by the controller's own
assignment, so applying a mode cannot cause a transition.

## Removed

- the 60-frame rAF pin loop
- all three `setTimeout` scrolls
- `pendingScrollRestoreRef` and its restore effect
- the scroll inside the external-update handler
- `isNearBottom()` as a second source of truth

Six writers and three timers become one layout effect and no timers. Initial
load stops being special: it starts in `following`, and the effect re-pins on
every commit while lazy content reflows, which is what the rAF loop
approximated.

## Migration

Two callers write `scrollTop` directly today and must go through the
controller, or the next commit will undo them:

- `BookmarkRail.tsx:104` (`container.scrollTo`)
- the search jump (`scrollIntoView`, `useChatSessionState.ts:711`)

Both become "anchor to this element at this offset", which additionally makes
them survive a store refresh landing mid-jump — neither does today.

`isUserScrolledUp` stays in the hook's public surface as a derived
`mode === 'anchored'`, so the "scroll to bottom" button
(`ChatInterface.tsx:399`) and `ChatMessagesPane` need no changes.

## Testing

The decisions are pure functions of numbers and go in `viewportMath.ts` with
Vitest coverage:

- desired `scrollTop` for each mode
- the drift rule that decides when to pick a new anchor
- the `clientHeight`-changed rule that suppresses a mode flip

The React wiring cannot be meaningfully unit-tested here — this project has no
jsdom and `vitest.config.ts` sets `environment: 'node'`. It gets manual
verification across seven paths:

1. initial load of a long session
2. streaming while parked at the bottom (should follow)
3. streaming while scrolled up (should not move)
4. prepend via "Load more"
5. "Load all"
6. search jump
7. bookmark jump

plus the iOS background/foreground case that prompted this.

The gated `scrollDebug` instrumentation from `9d28b5b`/`7658d5e` is re-added
for the rewrite, since it already answers exactly these questions, and removed
before the final commit.

## Out of scope

- CSS-native bottom pinning (`flex-direction: column-reverse`). It reverses DOM
  order, which breaks `BookmarkRail`'s `offsetTop` arithmetic, the search
  scroll-to-element path and `data-message-timestamp` anchoring, all of which
  depend on natural document order. Safari also has long-standing
  `column-reverse` scroll bugs, and Safari is the platform in question.
- Virtualised rendering of the message list.
- Changing the `INITIAL_VISIBLE_MESSAGES` render cap or the paging sizes set in
  `b3fa332`.
